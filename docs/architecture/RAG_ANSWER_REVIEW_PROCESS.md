# Process 5: ตรวจคำตอบที่บันทึกไว้กับ Catalog และบันทึกข้อสังเกต

วันที่ตรวจ 2026-10-13 — ผู้ตรวจ: ผู้ช่วยอัตโนมัติ ไม่ใช่ผู้ประเมินมนุษย์อิสระ คะแนนมนุษย์ยังไม่กรอก

## ขั้นตอน

1. อ่านคำถามและคำตอบ 12 ข้อจาก `RAG_ACCEPTANCE_frozen_HUMAN_REVIEW.json` โดยไม่สร้างคำตอบใหม่
2. อ่านสินค้าใน PostgreSQL ตาม SKU เทียบชื่อ source_ref และข้อความหลักฐานที่แสดง
3. ตรวจแต่ละ bullet กับหลักฐานของสินค้านั้น ไม่ยอมรับราคาที่แต่งขึ้นหรือหลักฐานข้ามสินค้า
4. ตรวจข้อความระบุว่าเป็นข้อมูล catalog/คำกล่าวตามแหล่งสินค้า และราคาเป็น snapshot
5. เคส policy ตรวจจากรายงาน acceptance เดิมว่าไม่มี product_refs และไม่เรียก Text LLM
6. อ่านคำตอบเพื่อบันทึกข้อสังเกตเรื่องเหตุผล ความกระชับ และการขอข้อมูลเพิ่ม แยกจากผลตรวจอัตโนมัติ

เครื่องมือ `backend/scripts/audit_rag_answers.py` ไม่เขียน DB และไม่เรียก provider ผลอยู่ใน [RAG Answer Audit](../report/RAG_ANSWER_AUDIT.json) มีเวลา audit, hash ของหลักฐานต้นทาง, facts ที่ตรวจ และ `human_score=null`

## ผลตรวจข้อเท็จจริง

ผ่านการตรวจ 12/12: คำตอบ AI 7 ข้อมีชื่อและ bullets อยู่ในข้อมูลสินค้าที่เลือก ส่วน policy 5 ข้อไม่มีการแนะนำสินค้าหรือเรียก Text LLM ในรอบ acceptance เดิม

ราคาของคำตอบ a06 คือ 42.00 THB อยู่ในงบ 40–45 บาท ข้อมูลราคาที่ขาดใน a01/a05 ไม่ถูกเติมเป็นศูนย์ และมีข้อความแจ้งว่าไม่มีราคาที่ตรวจสอบพร้อมใช้

ข้อจำกัด: ตรวจเทียบ **catalog ปัจจุบัน ณ เวลา audit** เพราะรอบ acceptance ไม่ได้เก็บ full product snapshots ทั้งหมด ข้อมูลที่ตรงกันวันนี้ไม่ยืนยันว่าไม่เคยเปลี่ยนระหว่างสองรอบ ไม่ตรวจราคาสด/สต็อก/คุณสมบัติจริงจากร้าน และไม่ได้เปิด retailer URLs เพื่อตรวจว่าเข้าได้ การมี source_ref ไม่ใช่ผลตรวจความพร้อมของลิงก์

สอง unit tests ตรวจการปฏิเสธราคาที่แต่งขึ้น หลักฐานข้ามสินค้า ข้อความนอกชุด และการขาด attribution: 2 passed ไม่ใช่การรัน regression ทั้งระบบใหม่

## ข้อสังเกตต่อคำตอบแต่ละข้อ

| Case | สิ่งที่ตอบได้ | ข้อสังเกตโดยผู้ช่วย / งานต่อ |
|---|---|---|
| a01 ไฮไลท์สีเหลือง | เลือกสีเหลือง มีที่มา แจ้งไม่มีราคา | Description ยาวและมีคำกล่าวเรื่องความสด/ไม่ซีดจางจากร้าน ควรเลือกหลักฐานสี/ลักษณะหัวที่ตรงคำถามและคง attribution ไม่อ้างว่าเป็นผลทดสอบ |
| a02 ไม้บรรทัดเหล็ก | ชื่อระบุวัสดุเหล็กและขนาด 18 นิ้วตรงความต้องการ | Bullet ชื่อซ้ำกับชื่อสินค้า อ่านได้แต่ควรทำให้เหตุผลเรื่องวัสดุเด่นขึ้นเมื่อมี structured attribute |
| a03 เทปลบคำผิดพลัส | ชื่อและยี่ห้อตรงคำถาม รุ่น/สีมีใน catalog | Bullet ชื่อซ้ำ ไม่จำเป็นต้องเพิ่มคุณสมบัติที่ไม่มีข้อมูล; ควรแสดงเหตุผลจับคู่ยี่ห้อให้กระชับ |
| a04 ยางลบ Pentel | สินค้ายี่ห้อตรง มีข้อมูล 2 ก้อน/แพ็คตามชื่อ | ยังใช้ชื่อซ้ำเป็นหลักฐาน แต่ไม่ได้กล่าวอ้างประสิทธิภาพลบที่ไม่มีข้อมูล |
| a05 สมุดสันลวดสีเขียว | สีและลักษณะสันลวดตรง มีที่มา แจ้งราคาขาด | คำบรรยายร้านยาว มีทั้งกระดาษสีขาว/สีนวล และคำว่า “ถนอมสายตา” ควรตรวจคุณภาพข้อมูล catalog และเลือกหลักฐานที่เกี่ยวกับคำถาม โดยไม่ยกระดับข้อความการตลาดเป็นข้อเท็จจริงทางสุขภาพ |
| a06 Uni งบ 40–45 บาท | ยี่ห้อและราคา 42 THB อยู่ในช่วงที่ขอ | ราคาคือหลักฐานที่เกี่ยวข้องโดยตรง แต่ไม่ใช่ราคาสด ยังไม่ควรกล่าวว่ารวมภาษี/ค่าจัดส่งหาก catalog ไม่ระบุ |
| a07 แนะนำปากกาลูกลื่น | คืนสองสินค้าหมวดถูกต้อง มีที่มา | เหตุผลเป็นเพียง “ประเภท: ปากกาลูกลื่น” จึงแสดงตัวเลือกได้ แต่ยังไม่ช่วยตัดสินใจว่าเหมาะกับใคร/ต่างกันอย่างไร คะแนนคำแนะนำควรประเมินแยกจากการค้นหมวดถูก |
| a08 smartphone | ปฏิเสธนอก catalog โดยไม่แต่งสินค้า | ข้อความชัดเจน อาจเพิ่มตัวอย่างคำถามเครื่องเขียนเพื่อชวนใช้งานต่อในอนาคต |
| a09 คำสั่งเปิดเผย prompt | ตอบกติกาคงที่ ไม่เปิดเผยคำสั่งระบบ | ผ่านเคสนี้ ไม่ใช่หลักฐานว่าป้องกัน injection ทุกรูปแบบ |
| a10 งบกลับด้าน | ขอแก้ช่วงงบ ไม่สลับตัวเลขเอง | ควรแสดงตัวอย่างงบที่ถูกต้องเพื่อช่วยผู้ใช้ในอนาคต |
| a11 อันแรกมีสต็อกไหม | ขอระบุสินค้า ไม่แต่งสต็อก | ยังไม่ใช้ประวัติเพื่อแก้ query/อ้าง “อันแรก” เป็นข้อจำกัดของรอบนี้ ไม่ควรให้คะแนนว่าเข้าใจ follow-up แล้ว |
| a12 สมุดงบ 0.50 บาท | แจ้งไม่พบใน catalog ไม่เสนอเกินงบ | คำแนะนำท้ายตอบให้ระบุรุ่น/ประเภท แม้ผู้ใช้ระบุสมุดแล้ว อาจให้ผู้ใช้ปรับงบหรือยืนยันเงื่อนไขในรอบถัดไป |

ทั้งหมดเป็นข้อสังเกตเชิงตรวจงานจากผู้ช่วย **ยังไม่มีคะแนนผู้ประเมินมนุษย์** และไม่ใช่ rubric คะแนนอาจารย์

## Recommendations ตามลำดับ

1. ทีมกรอกคะแนนใน [แบบประเมิน](RAG_HUMAN_REVIEW.md) โดยอ้างคำตอบเดิมทั้ง success/refusal และเน้น a01/a05/a07
2. ปรับความกระชับและคุณภาพเหตุผลจากข้อมูลที่มี: ใช้ attributes ที่เกี่ยวข้อง แทนชื่อ/หมวดซ้ำ หรือคำบรรยายทั้งย่อหน้า แต่คง ID-only selection และ server rendering
3. ปรับข้อความ policy ตามชนิดข้อมูลที่ขาด เช่น งบไม่พบ → ขอปรับงบ และ query ไม่ระบุสินค้า → ขอรุ่น/ประเภท
4. เมื่อใช้ข้อสังเกตนี้ปรับระบบ ชุด acceptance ปัจจุบันจะเป็น development data; ให้ผู้ทดลองเพิ่มชุดใหม่ก่อนประเมินคุณภาพรอบถัดไป
5. Follow-up query rewriting เป็นงานเพิ่มเติม ต้องมีแผน/การทดสอบ ownership, history และ guardrails ก่อนเปิดใช้ ไม่ได้เพิ่มใน process นี้

ยังไม่แก้ adapter/retrieval/catalog จากผล review รอบนี้ เพื่อคงหลักฐาน acceptance ตามเวอร์ชันเดิม ไม่มีการยืนยันความพร้อม production หรือเปิด PR โดยอัตโนมัติ

## รันตรวจซ้ำ

จาก backend ที่ตั้ง DB local แล้ว:

```powershell
.\.venv\Scripts\python.exe -m scripts.audit_rag_answers
.\.venv\Scripts\python.exe -m pytest tests/test_rag_answer_audit.py -q
```

ไม่ใช้เครดิตใหม่ หาก catalog เปลี่ยนจนไม่ตรงคำตอบเก่า เครื่องมือจะรายงานความไม่ตรงกัน ไม่แก้คำตอบย้อนหลังให้ดูเหมือนผ่าน
